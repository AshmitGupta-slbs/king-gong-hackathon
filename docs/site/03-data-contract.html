§ 03 · The data contract

One definition of a claim.

Ingestion, extraction, the gate, the transcript viewer and the export all depend on the same shapes. Where those shapes drift, citations stop resolving — so there is exactly one file that defines them, and a rule that nothing else may.

In one line: lib/types.ts defines a transcript segment and a claim; everything else imports from it. The model's output is a draft and the gate's output is a result — two different types, on purpose, so a model cannot declare its own output trustworthy.

Schemas are written in Zod and the TypeScript types are inferred from them, so the runtime validator and the compile-time type physically cannot disagree.

One definition, nowhere else

The failure this prevents is mundane and fatal: one part of the codebase inventing a slightly different shape for a segment. Ingestion writes start_ms, the viewer reads startMs, and citations silently stop resolving — at hour twenty, during integration, when there is no time to find it.

If the shape needs to change, it changes here, in the same commit as the code that needed it.

The transcript segment

The atomic unit every citation points into. One call produces an ordered list of these.

export const TranscriptSegmentSchema = z.object({
  id: z.string().regex(/^seg_\d{3,}$/, 'segment ids look like seg_000'),
  speaker: SpeakerSchema,
  start_ms: z.number().int().nonnegative(),
  end_ms: z.number().int().nonnegative(),
  /** VERBATIM provider output. The citation source of truth. */
  text: z.string(),
  /** Optional readability rendering. NEVER read in the gate. */
  display_text: z.string().optional(),
  /** Present only for stereo one-party-per-channel audio. */
  channel: z.number().int().optional(),
});

Two fields carry more weight than they look like they do.

TEXT
Verbatim, deliberately ugly

text is exactly what the speech API returned — lowercase, unpunctuated, transcription errors intact. It is the only thing the gate reads and the only thing quoted as evidence. We do not clean it up here.

DISPLAY_TEXT
Presentation only, and guarded

Reserved, and written by nothing today. Display rendering happens at the presentation boundary instead: the UI and the Markdown export each call readableFor(title) per segment, so the readable form is derived on demand rather than stored — a stored rendering can go stale against the rules that produced it. The field is kept for a future ingest-time cache. Either way it is never read by the gate and never quoted as evidence; text is the citation source of truth. The rendering rules are in §10.

The segment-id rules

Everything hangs off these, so they are stated as rules rather than left as habits.

RuleWhy
Assigned once, at ingestionAn id that can be regenerated is an id that can stop matching a stored citation.
Zero-padded seg_000Lexical order matches temporal order, so sorting anywhere is safe.
Ordered by start_msThe viewer, the player and the gate all assume it.
Never reused, never reorderedA share link from yesterday must still point at the same words.
Never invented by a modelThe model cites ids; it does not mint them. This is the difference between a citation and a guess.

PyAI does not hand back this shape, so the ingest mapper does real work rather than passing through. Four concrete differences, all measured rather than assumed (see §06):

PyAI returnsOur contract wantsMapping
id — integer, 0-basedseg_000 — stringzero-pad the index
start/end — float secondsstart_ms/end_ms — integer msMath.round(x * 1000)
speaker: "speaker_1"rep / prospectchannel index (stereo) or first-speaker heuristic (mono)
channel only when channel:trueoptionalabsent on diarized mono

Draft vs result — the important split

This is a deliberate divergence from the original spec, and it is the most important structural decision in the contract.

ExtractionDraft is what the model returns. Note what is not in it: no run_status, and no verdict on whether any citation held up.

export const ExtractionDraftSchema = z.object({
  summary: z.string(),          // free prose — a synthesis, not a claim
  intent: IntentSchema,         // { label, segment_ids }
  objections: z.array(ClaimSchema),
  next_steps: z.array(ClaimSchema),
  follow_up_email: FollowUpEmailSchema,
  key_moments: z.array(KeyMomentSchema),
  outcomes: z.array(OutcomeSchema).optional(),  // judgements on EARLIER calls' commitments
});

export const ClaimSchema = z.object({
  claim: z.string(),
  segment_ids: z.array(z.string()).min(1),   // ids that prove it
});

export const OutcomeSchema = z.object({
  item_id: z.string(),                       // an action item open for this account
  status: z.enum(['done', 'not_discussed']),
  note: z.string(),                          // what THIS call said, in this call's words
  segment_ids: z.array(z.string()),          // empty for not_discussed — absence has no line
});

outcomes is the one field that is not about this call. It carries the model's judgement on commitments made on earlier calls with the same account, each quoting back the stable id it was given. Two details are load-bearing: the id, because matching a commitment on restated wording is the fuzzy join the whole design avoids; and the note, because that is what the gate scores rather than the carried commitment's own text — scoring the latter would compare two different conversations and flag correct judgements as unsupported.

ExtractionResult is what the gate produces, and the only thing allowed to reach a screen. It adds the fields the model is not permitted to author:

run_status:  'shipped' | 'partial' | 'failed' | 'deadline'
rejections:  GateRejection[]        // what was dropped or flagged, and why
verdict:     'verified' | 'unverified'   // per claim
support:     number                 // 0..1, the tier-2 score, recorded for audit
evidence:    Evidence[]             // resolved from the transcript
A model must never be able to declare its own output shipped. Splitting the types is how that becomes structurally impossible rather than a code-review question.

Evidence and verdicts

Evidence is resolved by the gate, not supplied by the model:

export const EvidenceSchema = z.object({
  segment_id: z.string(),
  speaker: SpeakerSchema,
  start_ms: z.number().int().nonnegative(),
  end_ms: z.number().int().nonnegative(),
  text: z.string(),
});

Every field there is copied from the segment. Timestamps and quoted text never come from model prose — which is why a citation chip can be trusted to seek the audio to the right second, and why the quote under a claim is the call's words rather than the model's paraphrase of them.

The two verdicts mean different things, and the distinction is visible in the UI as an amber badge:

VerdictMeaning
verifiedEvery cited segment exists, and (for assertions) its text plausibly supports the claim.
unverifiedThe cited segments exist, but the text does not visibly support the claim. Ships with a warning rather than lying by omission.

Claims whose citations do not resolve at all get no verdict — they are removed from the output entirely. There is no third label, because a deleted claim is not a labelled claim.

Provenance

One field exists purely to stop us fooling ourselves:

/** Which registry provider produced the draft:
 *  'claude' | 'bedrock' | 'stub-heuristic' */
extracted_by: z.string().optional(),

It is persisted into every samples/*.result.json, surfaced in the UI header, and read by npm run check:ship, which fails while any shipped note was produced by the keyword stub. See §07.
