§ 06 · PyAI API truth

What the docs got wrong.

Everything on this page was probed against the live API rather than read from documentation. Where the two disagreed, the API won and the disagreement was written down. This is the most reusable page here for anyone else building on PyAI.

In one line: the sandbox key has more scopes than documented, the jobs endpoint omits the usage header everyone would build a meter on, streaming has two protocols and the published snippet lands you on the legacy one, and Hear will confidently invent sentences out of silence.

Source of truth: docs/api-truth.md in the repo. Six probe scripts under scripts/probe/ reproduce all of it.

Method

The reference spec we started from asserted that there was no live PyAI access outside the hackathon sandbox. That was the first thing to check, and it was false: the docs are public and POST /v1/sandbox/keys mints a working key with no auth, no signup, no card. Which meant every other assumption could be tested too, rather than designed around.

The rule for this page: an assumption that has not been probed is a risk, not a fact — and it goes in writing either way.

Scopes: the documented list is stale

A freshly minted sandbox key returns:

scopes: hear:transcribe, hear:stream, transcribe:jobs, voice:synthesize,
        omni:session, nova:run, amd:detect, amd:configure, amd:read, cast:render
FindingConsequence
transcribe:jobs is granted, though authentication.md lists only four scopes and the mint page advertises a shorter listThis was the single decision the whole architecture hung on. Had it been denied, ingest would have needed a stream-per-channel workaround.
No recap:* and no trace:*Recap and Trace are unavailable to us. So the "Recap writes your summaries" premise does not hold, and extraction is our own model call.
nova:run and cast:render are granted but 404 on every path we triedScopes for unshipped products. Ignore them.
GET /v1/models says the Speak model id is pyai-voiceNot pyai-speak, which is what we guessed first and what produced confusing errors.

Batch jobs — the path we actually use

POST /v1/transcription/jobs returns 202 with a job id; polling completes in about one 1.5-second interval for 30 seconds of audio. The terminal result carries text, segments, words, speakers and audio_seconds.

TRAP
No x-pyai-units on jobs

The header is absent on both the POST and the GET. It is present on the flat /v1/audio/transcriptions. A usage meter built purely on that header — the obvious design — would have silently displayed zero forever. Ours is driven by result.audio_seconds.

FREE BONUS
words[] has per-word timing

Undocumented in what we read: every word carries start, end and speaker. That is word-level highlight-as-it-plays for almost no extra work.

Large results are offloaded to a signed result_url rather than inlined, so any client has to handle both shapes.

Both speaker-separation modes work

ModeInputResult
channel: trueStereo, one party per channel6/6 segments correct, speakers: 2, channel 0/1 populated. Exact and model-free.
diarize: trueMono mixdown6/6 segments correct, speakers: 2, no channel field. Sortformer is good.

So stereo samples use channel:true — where rep/prospect is deterministic from the channel integer — and real mono uploads use diarize:true. The "analyse a call from any dialer" claim holds up.

For mono there is no ground truth for which speaker is the rep, so we use a stated heuristic: whoever speaks first is the rep, because the rep opens the call. Right on essentially every real sales call, wrong on some. The separation mode is persisted and shown in the UI so nobody mistakes a heuristic for a measurement.

LIVE RELIABILITY ISSUE
The diarize stage 500s in multi-minute windows

The job is accepted, transcription succeeds, and only diarization fails: {"status":"failed","error":"diarize: HTTP 500"}. Ruled out by direct experiment — MP3 vs WAV, numerals, multipart field order, our own encoder. The identical bytes succeed minutes later. It is time, not payload.

Two things follow. First, do not debug your audio when you see this, and do not A/B test it sequentially — the windows are long enough that whichever variant lands in a good window looks like the fix, which produced two false conclusions before interleaving settled it. Second, channel:true never touches that stage, so stereo upload is a working path while mono is failing.

lib/harness/retry.ts caps at 2 attempts and cannot outlast a multi-minute window, which is deliberate — the budget governor exists to stop runs, not to hammer a broken upstream. The run ends failed with the upstream error preserved. The mitigation that actually matters is that the five committed sample calls need no API call at all.

The asymmetry is confirmed on real audio, not just the samples. A genuine two-party dialer recording — stereo, 8 kHz — auto-selected channel mode and completed first try: 43 segments, two speakers, talk time 59.5 / 40.5. So while the mono path is unreliable, the stereo path is working today, and it is the mode the five samples use.

One quality note if you demo an overlapping-speech call: channel mode transcribes each track independently, so simultaneous speech interleaves into short fragments — "i don't" / "running" / "wanna give". That is more faithful than a diarizer guessing turn boundaries, not less, but it reads choppy, and it looks that way by design rather than because something broke.

And read the container from the bytes, not the filename. That real recording was named recording.mp3 and was actually RIFF/WAVE. Anything that picks a parser or declares a Content-Type from the extension is wrong on exactly the files people really have — lib/wav.ts sniffs the magic bytes and corrects the filename to match, because this codebase previously declared audio/wav for every upload unconditionally.

Streaming: there are two protocols, and the default is the legacy one

Not on our critical path — batch jobs own ingest — but the published snippet is wrong in a way that costs hours, so it is recorded.

The connect URL takes a protocol query parameter. Omitting it, which the published quickstart does, lands you on the legacy fusion-v0 route. Passing protocol=pyai-hear-v1 gives the documented one. Verified by running identical audio down both.

default / fusion-v0protocol=pyai-hear-v1
Frame typessession.created, transcript.partial, turn.end, usage.delta, transcript.finalpartial, partial_stable, speech_final, final, usage, config_ack
Flushing the tailOnly trailing silence (~1.8s) — every control frame rejected{"type":"commit"} works with zero trailing silence
EndpointingFixed; turns under ~1.8s merge, hard cap ~30sendpointing_ms (50–5000), settable mid-session

So the quickstart's if msg["type"] == "partial" does fire — but only with the protocol parameter added. As printed, against the default route, it silently matches nothing. The docs contradict each other here; the API settled it.

Other measured facts on that route: partial.text is a rolling ~16-word window rather than the utterance so far, so accumulating partials corrupts the transcript. utterance_id is not a join key — partials, turn.end and the final each carry a different id. And usage.delta bills active audio only, so 46.4s streamed billed as 29.8s.

⚠ Hear fabricates fluent text from silence

This is the most consequential finding in the project, and it came out of the live-mic streaming probe.

With nobody speaking, Hear repeatedly emitted confident finals — confidence 0.99+, endpoint_reason: silence — containing sentences that were never said. Measured input level: real speech RMS 0.219; the ambience windows that produced fabricated text, RMS 0.035.

Our citation gate treats segment.text as the source of truth for quoted evidence. So dead air on a call — hold music, mute, a pause while someone reads — can manufacture a quotable claim that no human uttered, and it will pass the gate, because the gate only checks that the quote matches the transcript.

The probe implements a check: --silence-floor (default 0.08) flags every final whose audio window never reached speech level. Any Hear-streaming ingest needs an input-level gate before segments are trusted.

Status for us: our ingest is the batch path, which is untested for this behaviour. scripts/probe/batch_silence_probe.py is written and would settle it — it submits speech · long digital silence · speech and checks whether any returned segment overlaps the silent window. Full discussion in §10.

Lowercase and unpunctuated, on both models

hi sarah thanks for making the time today i know you've been evaluating a few options

Confirmed on both pyai-hear-telephony (the jobs default) and pyai-hear — it is not a model-choice problem, it is how Hear returns text. This matters more than it looks: raw ASR casing is the difference between notes that read like a product and notes that read like a machine dump.

Our answer is in §10: store verbatim, apply two deterministic display passes — casing, then spoken-digit runs — each with its own guard, and refuse to let a model insert punctuation.

One oddity worth knowing: "fourteen hundred" comes back as "one four oh oh" on the jobs endpoint while the flat endpoint rendered "1400". On the stream, numerals=true works but applies only at finalisation — partials read "one four oh oh", the final reads "1400". Judge numerals from finals only.

CORRECTED — AN EARLIER CLAIM HERE WAS TOO STRONG
The request cannot control digit rendering

This page previously said numerals: true is silently ignored by the jobs endpoint. That overstated it. A counter-example turned up: a short clean mono clip of "the pricing came in around fourteen hundred a seat" returns "1400" — with no flag set at all. Four combinations were then run across WAV 16k, WAV 22k and AIFC 22k, covering both flag states, and every one returned "1400". (Four of the six possible cells, not all six: AIFC-with-flag and WAV-22k-without were not run. Each format and each flag state does appear, which is what the conclusion rests on.)

So the flag is not being ignored so much as it is not the variable. Re-running the committed pricing-pushback.wav bytes — stereo, channel:true — reproduces "one four oh oh" and "five oh oh oh" exactly as committed, flag or no flag. It is deterministic per file; something about length, mono vs stereo, channel:true or surrounding context decides it, and which one is untested.

The honest statement is therefore: digit rendering is unreliable and not controllable from the request, so it has to be normalised deterministically at the display boundary — which is what §10 describes. Do not try to "fix" the samples by enabling numerals and regenerating; that has been tested against the committed bytes and changes nothing.

Measured quality on synthesized audio: 8.4% WER after case and punctuation normalisation. The errors are the predictable ones — gong → gang, crm → erm, Q4 → q 4. Proper nouns and competitor names are where it slips, which is exactly what a competitor-tracker feature depends on.

Quota behaviour, and a misleading error code

Trying to regenerate sample audio on PyAI Speak produced this, and the label is wrong in both directions:

HTTP 429  {"error":{"code":"daily_cap_exceeded",
           "message":"Daily usage cap reached for this API key. Resets at 00:00 UTC."}}
ObservationWhat it rules out
Fired after ~30 rapid /audio/speech callsNot a per-day-zero from the start
A single call minutes later succeededNot a hard daily exhaustion
~10 calls at 250 ms spacing 429'd again; so did 6 attempts backing off to 24 sNot a short burst limit either
Isolated calls kept succeeding throughout—

The workable reading: Speak on a sandbox key has a small allowance that sustained generation exhausts. No Retry-After header is sent, so there is nothing to honour — the field is wired up in our client and simply stays undefined here.

Hear was unaffected throughout, including while Speak was fully blocked. Transcription — the thing the product depends on, and the larger meter — was never at risk.

Quota is per key/org: a freshly minted sandbox key comes back with a different org_id and a fresh allowance. Minting is one unauthenticated call, so a blocked build is recoverable — but that is a recovery path, not a strategy.

THE EXPENSIVE LESSON
A partial regeneration is worse than none

The failed Speak run left three calls on 24 kHz PyAI audio paired with transcripts from the 16 kHz say audio. Everything still looked correct — but every citation would have jumped to the wrong moment, which is a total product failure presented as a working demo. It is now asserted by npm run check:ship as an audio/transcript drift check, and npm run reindex:samples rebuilds the manifest from disk when a run dies partway.

The probe scripts

Six standalone Python probes under scripts/probe/. They need no app, and each one answers a single question.

ScriptQuestion it answers
probe.pyThe H0 gate: does a sandbox key get diarized segments with timestamps at all?
probe2.pyDo both separation modes work? Does model choice affect punctuation?
hear_stream_test.pyThe streaming rig — transcript → speech → real-time stream → WER scoring, plus --mic for live input
eos_probe.pyWhich end-of-stream signal actually makes Hear flush its last utterance?
batch_silence_probe.pyDoes the batch path fabricate text from silence? Written, not yet run.
batch_modes_probe.pyDo the two batch presets behave as documented on PyAI's own telephony samples, and does numerals take effect?

Two environment notes that cost time and are cheap to pass on: python.org's Python 3.14 ships without a CA bundle, so probes need SSL_CERT_FILE=/etc/ssl/cert.pem; and sounddevice's macOS wheel bundles PortAudio, so live-mic capture needs no Homebrew.
