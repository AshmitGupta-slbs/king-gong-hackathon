§ 09 · Run & verify

Run it, then check it.

Two commands to a working app with five analysed calls. One more to prove the claims on the rest of this site rather than take them on faith.

In one line: curl -fsSL …/install.sh | bash — it sorts out Node, clones, installs, asks for your keys, and proves the pipeline on a real call. Or by hand: npm ci && npm run dev. No key, no signup, no database server, nothing to compile.

Then npm run verify runs all 252 suite checks plus the 27-item ship checklist. Expect exactly one red line: the provenance gate, which stays red until the committed samples are regenerated by a real model.

Setup

One command on a machine that has never seen this repo. It checks Node, installs a newer one if needed, clones, runs npm ci, then hands over to setup.sh — which reads the scopes off your PyAI key, recommends a notes engine from what that key can actually do, and finishes by transcribing and analysing a real call so "configured" and "working" are never confused.

curl -fsSL https://raw.githubusercontent.com/AshmitGupta-slbs/king-gong-hackathon/main/install.sh | bash
cd king-gong
npm run dev      # web app  -> http://localhost:3000
./kg             # terminal UI

Already cloned? npm ci && ./setup.sh. Re-running setup.sh is safe and keeps every answer already given.

The prompts once answered themselves, and that is worth recording

Every prompt in setup.sh was read -r -p "..." VAR || true. Under curl | bash, bash reads the script from stdin, so stdin is already spent by the time the prompts run: each read returned instantly at EOF, || true discarded the failure, and the empty answer was recorded as though a human had pressed Enter. A teammate got a run that asked him nothing, silently selected the keyword stub, and announced "Setup complete".

Two changes, and the second is the one that matters: every prompt now reads from /dev/tty explicitly, so it opens the terminal itself rather than trusting inherited stdin; and a prompt that cannot reach a human never counts as an answer — it hands off with the install intact and writes no .env.local at all, because a file saying PYAI_API_KEY="" looks like a decision somebody made.

The reason it shipped is the interesting part. The development environment has no TTY, so the interactive path was tested with the re-exec disabled and piped answers — which is precisely the broken path. Prompt behaviour can only be tested on a pseudo-terminal:

expect -c 'spawn ./setup.sh; expect "PyAI API key*" { send "x\r" }; expect eof'

check:ship now asserts that no prompt reads inherited stdin and none swallows its own failure — a guard on the pattern. The behaviour is proved by the command above, which cannot join the suite because it clones and installs.

The Node floor is 22.13, not 22.5 — and the repo used to get this wrong

engines declared >=22.5.0, because that is the release where node:sqlite first appeared. But it stayed behind --experimental-sqlite until 22.13, so every Node from 22.5 to 22.12 satisfied the declared requirement and then threw ERR_UNKNOWN_BUILTIN_MODULE at the first database call — the failure shape where everything looks fine until it does not.

Measured with nvm rather than recalled: 22.12.0 throws, 22.13.0 loads and DatabaseSync is a function. So scripts/node-check.cjs asks Node whether it can actually open a database, and uses the version only to write a better error message. It is plain CommonJS with no imports, because its whole job is to run on the wrong Node, before npm ci has installed anything.

The terminal UI

./kg is the same product without a browser. It reads the database directly, so browsing works with no server running; analyse goes over HTTP so the dev server stays the only writer — withLock is a per-process Map and would not serialise two processes, and SQLite in WAL mode tolerates many readers but not two writers.

CommandDoes
./kgInteractive: pick a call, read its notes, hear the moment
./kg callsEvery call with status, engine and duration
./kg show <id>Each claim with its cited lines underneath, the transcript, and what the gate rejected
./kg show <id> --mdThe same call through lib/export.ts — byte-identical to the web export
./kg analyse <file>Live progress rows from the NDJSON stream, then the cited notes
./kg doctorNode, env file, credentials, key scopes, data/ writability, which engine would run

Hearing the cited moment survives the port, which took a workaround. afplay ships on every Mac but has no seek — only -t, a duration from the start of the file — and there is no ffmpeg, ffplay or sox to fall back on. So instead of seeking, the clip is cut in Node: parseWav, slice pcm16 at a frame-aligned byte offset, buildWav, play that. Both helpers already existed in lib/wav.ts. Frame alignment matters rather than being pedantry: an unaligned slice shifts the channels against each other, which on a one-party-per-channel call drifts the two speakers apart.

Verified by round-trip rather than by ear: the sliced clip was sent back through Hear and the transcription came back word-for-word identical to the segment it was cut from.

Five fully-analysed sample calls are already there. That works with a completely empty environment because the sample audio, transcripts and notes are all committed, a PyAI sandbox key mints itself on first live use, and storage is Node's built-in SQLite — so there is no service to start and no native module to build.

Measured on a clean copy: 5 s install, 6 s to serving, 11 s total. All pages 200, five calls loaded, and no PyAI key minted — because viewing bundled samples touches no network.

Adding credentials

Transcription needs nothing — the sandbox key handles it. Notes need a model. The provider is auto-detected from whatever is present.

PYAI_API_KEY with recap:read + LLM_PROVIDER=recaprecap — PyAI writes the notes, so no model of your own is needed. Never auto-detected, because a PyAI key exists on every machine. Check it with npx tsx scripts/probe/recap-probe.ts

export AWS_ACCESS_KEY_ID=...  AWS_SECRET_ACCESS_KEY=...  AWS_REGION=us-east-1
npm run extract:samples     # regenerate all five sets of notes
npm run check:ship          # should now pass fully

extract:samples deliberately reuses the committed transcripts, so it costs no TTS and burns no PyAI minutes. .env.example documents every option including the gate threshold and budget caps.

The split between samples and extract:samples is deliberate: regenerating notes is cheap and common, regenerating audio is expensive and rare. And reindex:samples exists because a run that dies partway leaves the manifest describing the previous state while the files describe the new one — which is how three calls once ended up paired with the wrong transcripts.

What each suite actually proves

37 CHECKS
test:gate

A fabricated segment id is dropped and logged. A real-but-unsupporting citation ships flagged. A partly-bad list keeps the good ids. Nothing surviving reports failed, not partial. Evidence text and timestamps come from the segment.

127 CHECKS
test:harness

Budgets throw before the call, naming the cap. Retries are capped and carry the reason forward. A DeadlineError is never retried. Locks serialise and release. A killed run reconciles to failed. All four exit statuses demonstrated.

46 CHECKS
test:readability

Casing, acronyms and proper nouns are fixed; and the property that matters — all 50 real transcript segments survive word-for-word identical, so the display layer can never alter evidence.

None of the harness tests use a fake provider. Failures are induced through real code paths — a fixture that does not exist, a one-token budget — so what passes is the shipping loop.

Running the probes

Six Python probes under scripts/probe/, independent of the app. They hit the live API, so they cost quota.

# python.org Python ships without a CA bundle — this is required
export SSL_CERT_FILE=/etc/ssl/cert.pem

python3 scripts/probe/probe.py           # H0: does a sandbox key get diarized segments?
python3 scripts/probe/probe2.py          # both separation modes, model choice

# the streaming rig has its own venv (sounddevice bundles PortAudio, no Homebrew needed)
./scripts/probe/.venv/bin/python scripts/probe/hear_stream_test.py --mic
./scripts/probe/.venv/bin/python scripts/probe/batch_silence_probe.py

That last one is the unrun probe that would settle the open silence-fabrication question on our own ingest path. See §10.

Demoing it

docs/demo-script.md has five beats, a failure playbook and a "do not" list. The short version:

  1. Open a sample — zero setup

    No key, no signup, five analysed calls already there.

  2. Upload a real call, early

    Because the usage counter is the number people assume is fake. Watch it move.

  3. Click a citation, then stop talking

    Let the audio play those few seconds out loud. The silence is the moment the room understands it.

  4. Press "Test the gate"

    Fabricated claims get dropped and logged in front of the audience. Say plainly that the claims are hand-written and no model was called — we are demonstrating the gate, not faking a hallucination.

  5. Export, then run the harness suite

    Notes with quotes and timestamps inline, plus a table of everything the gate rejected.

DO NOT
Demo with the STUB EXTRACTOR badge showing

If that badge is visible, the notes came from keyword rules rather than a model. check:ship will refuse to pass. Fix the credential first.

SymptomCause and fix
Counter reads 0.0 minCorrect on a fresh clone. Bundled samples burn nothing, so they count nothing. Process a call and it moves.
STUB EXTRACTOR badge showingNo model credential detected. Set one and run npm run extract:samples.
Audio will not autoplayBrowsers block autoplay until a user gesture. Press play once manually; the seek already happened.
