Marking our own homework.

This build is scoring itself, so treat every number as a claim by an interested party. What makes it worth reading is that each one names the file or the command that produces it. The brief asks for exactly this document — "go criterion by criterion and name where you're weak, with evidence. Don't be diplomatic about it." So the weak parts are named, and the last section says which one gets the remaining time.

Product pull — 30% → 26

The reference is explicit that this criterion is answered by the citation mechanic and not summary quality: "summaries are table stakes; every competitor already has one."

Every claim carries segment_ids, and the gate resolves them against the transcript before anything ships. A claim citing a line that does not exist is deleted. Timestamps and quoted text come from the segment, never from the model's prose. Click a citation and the audio seeks to that second.

Three things go further than the brief asked: the gate's rejections are published as a first-class panel rather than hidden; unverified claims ship flagged rather than dropped, with the support score visible; and commitments now carry between calls and can only be closed by evidence — a model marking a prior action item done must quote the line on this call that says so.

THE DEDUCTION
What a stranger meets on their first run

The five bundled sample notes were hand-authored, not model-written — extracted_by reads demo-fixture and the app says so in three places. And npm run verify fails on a clean clone, on the provenance gate, for that reason. Both are honest. Both are also the first thing a stranger sees, and "would a stranger switch tomorrow" is precisely a question about first impressions.

One command with a real credential fixes both: npm run extract:samples.

Demo magnetism — 25% → 19

The moment exists, and it is the one the build reference predicted: it names click-a-citation-and-the-audio-jumps as "the single feature most likely to be your demo's 'oh damn'". It works, it is instant, and the transcript scrolls to the line and pulses it.

The harness has a stage moment too — Test the gate feeds fabricated citations through the real gate and shows what it dropped, which is the brief's own advice for making Loop depth visible. And the CRM payload tab shows the exact JSON a push would post, with a check that fails the build if anyone adds a way to send it.

What is missing is the part the brief cares about most. The demo has never been rehearsed or timed on the real setup path — check:ship prints that omission itself. And docs/hero.png, the README's flagship image, shows the stub-extractor banner, which this project's own demo script forbids: "Do not demo with the STUB EXTRACTOR badge showing." It also predates the CRM payload tab and the action-items card, so it shows a UI that no longer exists.

API gravity — 20% → 12

The counter is real and honest: top bar, unmissable, counting audio seconds, tokens, calls and claims blocked — and replaying a committed sample deliberately records nothing, so the number only moves when work actually happens.

Three things count against it, and none are small.

And the shape is per-call, not daily. The brief's own model of gravity is dictation, hit dozens of times a day. Deal notes are a few times a week.

Loop depth — 15% → 14

All seven parts exist as named files with a stated contract, and each has a section in the suites — see § 05. Two worth pointing at specifically.

The gate's asymmetry is deliberate and documented: list claims with unresolvable citations are dropped, singleton deliverables are flagged and force run_status: partial. That is a decision somebody made, not a default.

The budget governor was wrong until recently and is now right. It estimated input tokens from the transcript alone, ignoring the system prompt and every context block — 14 estimated tokens against a real prompt of 980 on a two-line call. It now sizes the message actually sent. A cap that cannot see the text it is capping is not a cap.

The single point off: npm run verify does not include test:store (66 checks), because that needs a configured backend. Reasonable — but it means "the one command" is not literally everything.

Craft — 10% → 8

193 files, 17,317 lines of TypeScript, 47 commits. Five suites totalling 252 checks, a 27-item ship checklist, and four operational checks. Boundaries are enforced rather than asserted: the build fails if a vendor SDK is imported outside the providers directory, if a process.env read under lib/ is undocumented, if a credential appears in a committed file, or if a HubSpot client appears anywhere.

The two points off are the documentation. Until this commit the README pointed at a file that does not exist, gave the wrong path for the call page, omitted nine of nineteen scripts and two whole directories, and carried check counts matching neither the code nor this site. This site was four commits stale, and its generator would have re-stamped the old product name across all ten pages on the next build. Fixed now — but "would we be proud of this in public" is a question about the whole artefact, and a stranger reads the docs first.

The asterisk is the brief's own condition, and it has not been met. The requirement is a setup "tested on a machine you haven't touched, not your dev laptop", timed, by someone who has not seen the code. That run has not happened. Everything suggests it would pass — but the checklist asks for evidence, and "we're fairly sure" is not evidence. One genuine risk a clean machine would expose: Node must be ≥22.5.

Scope, and one flag

The MVP scope is met. One item is softer than it reads: "transcript with speaker names" ships speaker roles — exact for stereo, an explicitly stated heuristic for mono — with real names only when a CRM record supplies them.

🚩 SCOPE CREEP, FLAGGED LATE
The CRM payload preview

The brief lists "no CRM sync" as explicitly out of scope, and instructs: "if a request would add one of these, flag it as scope creep against the ship checklist rather than building it quietly."

What was built is not a sync — no client, no credential, no code path that could reach a portal, and a check that fails the build if any appear. The letter of the rule holds, and arguably the guarantee is stronger than the rule asked for. But the instruction was to raise the flag before building, and that did not happen; it went into a commit message instead. This is the correction.

One divergence from the reference worth recording. The build reference anticipated an opengong-lite-builder.skill installed into .claude/skills/ — a skill for the tool building the product. This repo has none. It instead put skills at runtime: six SKILL.md files loaded into the extraction prompt, so the judgement about what counts as a real objection lives in markdown a salesperson can edit. Deliberate, and recorded as a divergence rather than presented as compliance.

The weakest thing, and what to do about it

API gravity, 12/20. Lowest score, a fifth of the total, and the one the brief warns is easiest to under-invest in because it never shows up in a screenshot.

HIGHEST LEVERAGE
Run one real extraction

npm run extract:samples with the Bedrock credential already configured. Makes the bundled notes model-written, clears the only red in verify, moves the token counter off zero, and unblocks a hero screenshot without the stub banner. Product pull, Craft and Demo magnetism, in one command.

SECOND
Make the demo burn minutes on stage

Beat 2 uploads a real file with a live key. Rehearse it, and make sure the counter visibly moves — the brief says this in as many words.

THIRD
Re-probe Speak

OPENGONG_TTS=pyai-speak is one variable and the code is written and tested. It was defaulted off after a real 503, not by choice.

NOT A CODE CHANGE
Time the setup on a clean machine

The only checklist item still carrying an asterisk, and the cheapest to close. Someone who has not seen the code, a machine nobody has touched, a stopwatch.
