§ 07 · Extraction & providers

Providers are config, not code.

Which model or API each step calls is a line of configuration. Steps ask a registry for "the current speech provider"; they never import a vendor SDK. That is what makes the zero-setup demo possible and the Bedrock swap a one-liner.

In one line: three capabilities (speech-to-text, extraction, text-to-speech), eight providers behind them, resolved by lib/registry/index.ts. Extraction auto-detects which model credential you have and falls back to a loudly-labelled keyword stub if you have none.

The rule is enforced by a test: check:ship fails if any file outside lib/registry/providers/ imports @anthropic-ai/*. A registry that can be bypassed is decoration.

The capability registry

Every provider adapts its vendor's response into our data contract before returning. Nothing outside the providers directory ever sees a raw vendor payload — which is what turns a provider swap into a one-file change instead of a rewrite.

// lib/registry/index.ts — ★ the one file you edit to swap a provider ★

export const REGISTRY_CONFIG = {
  stt:     (process.env.OPENGONG_STT ?? 'pyai-jobs'),
  extract: providerFromEnv() ?? detectExtractProvider(),   // LLM_PROVIDER
  tts:     (process.env.OPENGONG_TTS ?? 'macos-say'),

  extractModel:  process.env.LLM_MODEL || 'global.anthropic.claude-sonnet-4-6',
  extractEffort: process.env.OPENGONG_EFFORT ?? 'high',
  budget: { maxInputTokens: 180_000, maxUsd: 1.0, /* … */ },
  supportThreshold: 0.18,
  maxAttempts: 2,
};

Note that the gate's support threshold and the budget caps live here too. The reference spec asked for budget caps "in the capability registry layer", and keeping every knob on one surface means a demo can be retuned with environment variables and no rebuild.

The two variables that choose the model are named LLM_PROVIDER and LLM_MODEL — deliberately the names used by the other services this deploys alongside, so one host configuration works everywhere. Spelling is forgiving: case is ignored and any run of non-alphanumerics folds to _, so anthropic_bedrock, anthropic-bedrock and ANTHROPIC BEDROCK all resolve.

A TYPO MUST NOT BECOME A SILENT DOWNGRADE
An unrecognised LLM_PROVIDER throws

It does not fall back to auto-detection. With a silent fallback, LLM_PROVIDER=antropic_bedrock would resolve to the keyword stub on a host with no other credentials — and the app would then serve stub-generated notes wearing the appearance of model output, which is the single thing this product argues against.

This repo shipped that exact failure once in another guise: the upload route cast an unvalidated form value, so anything that was not literally 'channel' fell into a bare else and diarized, making a typo indistinguishable from a deliberate choice. Same shape, same remedy — validate, never coerce.

LLM_MODEL is optional, and its default is deliberately a cross-region inference profile rather than a plain model name — see the four shapes below for why that distinction decides whether a request works at all.

The fixture provider deserves a note, because it is the reason a stranger can clone this repo and see five analysed calls with no key. It replays samples/<id>.stt.json — and it reports no usage, because replaying a cached file burns nothing. Reporting fake minutes there would make the usage counter a lie, which is the one thing this product cannot afford.

How extraction works

PyAI's Recap would nominally do this job, but the sandbox key carries neither recap:read nor recap:configure, and Recap needs an org add-on. PyAI's own conversation-intelligence guide says to bring your own model for this step, so we do.

NO JSON REPAIR LOOP
Schema-forced output

messages.parse() with output_config.format guarantees a schema-valid object. There is no free-text JSON parsing and no parse-and-repair retry anywhere in this repo. The retry that does exist is for semantic failure — a citation that does not resolve.

DEFENCE IN DEPTH
Re-validated at the boundary

The parsed output is re-checked against the Zod schema in the provider. Structured outputs should already guarantee the shape, but validating means a provider quirk fails loudly there rather than flowing into the gate and producing a confidently wrong result.

Both real providers share their prompt, request shape and response handling via extract-shared.ts. They differ only in client construction and model id — because the prompt is the part that decides whether citations resolve, and two copies drifting apart would mean two different products behind one gate.

One deliberate omission in the schema, explained fully in §10: segment_ids is not enum-constrained to the call's real ids, even though it could be. Constraining it would make a fabricated citation structurally impossible — and would also mean the gate could never fire, which would cost us the one honest, visible proof that it works.

Wiring up Bedrock

Written and type-checked, but never executed against real AWS. Three facts established without credentials:

  1. Use the Mantle client, not the legacy path

    We use AnthropicBedrock — the Bedrock Runtime Messages API — matching the reference implementation this deployment shares with its sibling services. Authentication is pure AWS SigV4 from the credential chain: no gateway, no baseURL override, no API key, and ANTHROPIC_API_KEY is never consulted on this path.

  2. Structured outputs are supported

    Verified from the feature list, and messages.parse was confirmed present on the Mantle client by inspection. That was the only feature extraction depends on. Nothing this app uses is on Bedrock's unsupported list.

  3. The constructor arg is awsSecretAccessKey

    Not awsSecretKey, which is what the legacy client and some documentation examples use. Found by inspecting the package rather than at 7am on demo day.

# Nothing to pass explicitly — the SDK resolves credentials and region itself.
export AWS_ACCESS_KEY_ID=...
export AWS_SECRET_ACCESS_KEY=...
export AWS_REGION=us-east-1

npm run extract:samples      # regenerates all five sets of notes

One thing no code can arrange: Anthropic model access must be enabled in the Bedrock console for that region. The provider distinguishes that from a wrong model id, because both arrive as an HTTP error and the instinct on either is to re-check the keys:

Bedrock denied access to anthropic.claude-opus-5 in us-east-1.
Enable Anthropic model access in the Bedrock console for this region,
and check the IAM principal can call bedrock:InvokeModel.

Bedrock takes four shapes of model id, and they are not interchangeable

This is where a day went. Getting it wrong produces a 404 not_found_error that reads exactly like "this region does not serve that model", so the natural response is to change the region — which never helps.

HOW THIS WAS ACTUALLY RESOLVED
Two sessions argued the wrong question

The provider originally prefixed every id with anthropic., which turned a profile id into anthropic.3s3wyt6beb2x — a shape Bedrock cannot interpret. Two sessions then spent a long exchange arguing from documentation over whether ids are bare or prefixed, each producing real citations, each partly right. Neither position was the answer: it depends on which of the four shapes you hold, and no amount of reading about "prefixed vs bare" could reach that.

What settled it was reading a working implementation — the sibling service's _bedrock_invoke_model_id, which normalises by shape and carries an executable spec. That is ported here 1:1, with its own tests mirrored, and it took minutes.

Two deliberate divergences from it: a bare id with no resolvable account throws rather than being sent unexpanded with a warning, because the reference's own tests show that path produces exactly the 404 that misleads; and a leading claude- is treated as a foundation id, which the reference never needs because its Bedrock path is always handed a profile id, while ours defaults to claude-opus-5.

npm run check:model now prints input → resolved per candidate before probing it, so a mangled id is visible rather than inferred, and separates "not offered in this region" from "offered but not enabled for you".

THE NEXT DEPLOY FOUND THE NEXT LAYER
A foundation id is not invocable at all on an account without provisioned throughput

With the shapes handled correctly, the deployed app returned a different 400 — and a far more useful one: "Invocation of model ID anthropic.claude-opus-5 with on-demand throughput isn't supported. Retry your request with the ID or ARN of an inference profile that contains this model."

That is the same failure the reference's remap table exists for, on a model its table does not list. The table was enumerating a rule rather than expressing it, so the rule is now expressed: every anthropic.claude-* id is routed through global., which is an inference profile. Non-Claude foundation ids still pass through untouched, so the reference's own behaviour is preserved.

The first attempt at fixing that was to refuse to start without an explicit LLM_MODEL. That was wrong too, and worse: it turned a configuration the sibling services run happily — everything blank — into a hard failure. The right answer was the one those services already had: a default that is itself an inference profile. So the default is now global.anthropic.claude-sonnet-4-6, which needs no account id, no ARN and no provisioned throughput.

Same story for AWS_ACCOUNT_ID: it is optional. When a bare profile id does need one, it comes from sts:GetCallerIdentity — cached, failure included, so a broken lookup costs one call per process rather than one per request. Requiring the variable, as an earlier version did, was again a preference imposed on a setup that already worked without it.

One further consequence of following the reference: it drives Bedrock with tool calling and never sends output_config or thinking, so structured outputs are unproven on this exact endpoint. Extraction therefore asks for structured output first and, only if those parameters are rejected, retries once as a single forced tool call whose input schema is the same Zod schema. Same contract, same gate, no JSON repair — and a 404, an auth failure or a refusal still propagates rather than being masked by a second attempt.

Still unverified end-to-end until a model call actually succeeds: whether messages.parse() behaves identically on Mantle, and whether output_config.effort is accepted there. Flagged rather than assumed — the habit that would have caught both of the mistakes above.

Provenance enforcement

The stub exists so that the UI, routes, export and harness verification were not blocked behind a credential. That creates an obvious hazard: stub output quietly becoming the demo. So provenance is enforced by tooling rather than by remembering.

What the keyword stub actually does

For completeness, since it is what you see on screen today. It derives claims from the transcript using keyword rules — objection cues, competitor names, next-step cues — which means every citation resolves by construction, so the gate runs for real and the UI gets realistically-shaped data.

It is not a model. It does not reason about the call. Its summary opens with "[Heuristic stub — no model was involved]", and it reports zero tokens, because it consumed none.

It also earns its keep as a demonstration that the registry works: swapping the extraction engine is one line of config, and nothing outside lib/registry/providers/ changed to accommodate it.
