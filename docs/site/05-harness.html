§ 05 · The harness

Seven parts, all real.

Anyone can call a transcription endpoint. The difference between a demo and something people trust is the engineering around the loop — and the only way to claim it is real is to force each failure and show the record it leaves.

In one line: every run ends in exactly one of four named statuses, budgets stop runs before they overspend, retries are capped and carry the reason forward, writes to one call are serialised, and no run can vanish without leaving a record — including if you kill the process mid-run.

39 checks in npm run test:harness, all passing. None of them mock a provider: failures are induced through real code paths.

Why the harness is the moat

The wrapper is not the interesting part. A transcription call plus a model call is an afternoon. What takes the time is everything that happens when one of them misbehaves — and that is also what decides whether the citation feature is trustworthy or cosmetic.

A gate that can be bypassed by a retry loop is not a gate. A budget that is logged after the fact is not a budget. So each part below has a column for what makes it real, because the failure mode for all seven is looking implemented.

What makes a retry "aimed"

Most retries are "try the identical thing again and hope". That is useful for a network blip and useless for a model that produced structurally valid output with a fabricated citation — retrying the same prompt gets you the same class of answer.

So the gate's actual complaint is threaded into the next attempt's prompt:

// lib/registry/providers/extract-shared.ts
if (req.priorFailure) {
  user +=
    `\n\nYour previous attempt was rejected by the citation gate:\n${req.priorFailure}\n` +
    `Fix exactly that. Cite only ids present in the list above, and drop any claim you ` +
    `cannot ground in a real segment rather than re-citing a missing one.`;
}

The trigger is narrow on purpose. A retry is spent only when the gate had to delete claims for citing segments that do not exist. A flagged-but-shipped claim does not burn an attempt — it is a legitimate outcome, not a failure.

Two things are never retried, both because retrying is the opposite of what they mean:

DeadlineError — the budget said stop a fatal 4xx — bad scope or bad request

The budget governor

Deliberately vendor-neutral: it knows about tokens, seconds and dollars, not about Anthropic. Three caps, all checked before the call:

maxInputTokens   180_000     // projected input would exceed → stop
maxOutputTokens   16_000
maxWallClockMs   180_000     // elapsed already over → stop
maxUsd               1.0     // projected spend would exceed → stop

The pre-call input estimate is a character heuristic (~3.6 chars/token), which is approximate on purpose — the alternative is a network round-trip to a token counter before every call, buying precision nobody needs. Actual usage is recorded after each call and gates the next one, so the estimate cannot drift far.

Breaching any cap throws a DeadlineError naming the cap, the loop catches it, and the run exits deadline with the reason attached. Caps are overridable per run, which is what makes them testable without mutating global config.

The failure invariant

The ordering is the whole feature:

  1. Write the row first

    openRun() happens before the STT call, before anything. Status running.

  2. Do the work

    Whatever happens — success, provider failure, budget deadline, uncaught throw.

  3. Close the row in a finally

    Exactly one terminal status, plus the error text and a budget snapshot. This runs even when the body throws.

  4. Reconcile orphans on boot

    A row still marked running from a previous process is, by definition, a crash. reconcileOrphanRuns() turns it into a failed record carrying "process exited before this run completed". Called on every home-page load.

The point is not tidiness. It is that partial and failed are only trustworthy if the alternative — a run that simply vanished — is impossible.

What each group asserts

·
Budget governor — 6 checks

A request inside the caps is allowed. Projected input over cap throws DeadlineError naming maxInputTokens. Projected spend over cap names maxUsd. Elapsed wall clock over cap names maxWallClockMs. Dollar accounting matches list pricing (1M input + 100k output = $7.50). The token estimator is sane.

Bounded aimed retry — 10 checks

Succeeds first time without retrying. Retries when validation rejects. First attempt gets no priorFailure; the second receives the specific reason. Attempts are capped — no infinite loop. Returns the last value when attempts run out, and records every failure reason. A throwing step is retried to the cap then rethrown. A DeadlineError is tried exactly once. A fatal 4xx is tried exactly once.

Safe parallelism — 6 checks

Same key: the second operation waits (asserted on interleaving order, not timing). Different keys run concurrently. A holder that throws does not wedge the queue behind it. Lock entries are released once drained. parallelMap respects its concurrency limit and preserves input order in its results.

Failure invariant — 4 checks

A stale running row is reconciled on boot, becomes a failed record, and carries a reason. A properly closed run is never touched by reconciliation.

The named loop, end to end — 13 checks

A good run ends shipped or partial, persists segments, produces an extraction, closes its row with that status, and records a budget snapshot.

A provider failure ends failed, reports the error to the caller, still leaves a row, attaches the reason, and closes the row — no silent hang.

And the budget proof: a run with maxInputTokens: 1 exits deadline, names the cap it hit, and is recorded like any other run.

What writing the tests actually found

Two real bugs, which is the argument for forced-failure testing over assertion-by-comment.

BUG 1
The lock map grew forever

Cleanup compared locks.get(key) against undefined — never true at that point, so entries were never released and the map grew for the lifetime of the process. Now it compares identity against the stored tail, which also avoids orphaning a queued waiter.

caught by: "lock entries are released once drained"
BUG 2
A spread overwrote the field beside it

In the gate, { claim, segment_ids: v.segment_ids, ...v } silently overwrote segment_ids and leaked an internal missing field into shipped output. Now written explicitly.

caught by: TypeScript, once strict-checked
