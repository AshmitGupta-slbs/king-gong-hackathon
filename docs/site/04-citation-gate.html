§ 04 · The citation gate

A gate that actually blocks.

Everything else in this repo is plumbing around one function: runCitationGate(). It is a blocking check that deletes model output, logs why, and downgrades the run status. Not a comment saying TODO: validate.

In one line: before any note reaches a screen, every citation is checked twice — does the cited line exist in this call, and does that line actually back up the claim? Failing the first deletes the claim. Failing the second ships it with a visible warning.

Every deletion and every flag is written to gate_rejections with a reason, and shown in the UI. 21 automated checks hold this behaviour in place.

Tier 1 — does the citation resolve?

Exact, cheap, and non-negotiable. Every segment_id a claim cites must exist in this call's transcript. There is no fuzzy matching and no nearest-neighbour fallback.

A claim citing seg_412 on a ten-segment call is not a claim with a typo. It is a claim about something that did not happen, and it is removed.

Tier 2 — does the segment support the claim?

The reference spec flagged this as a genuine design decision with several defensible answers — keyword overlap, an LLM-as-judge second pass, or a human-in-the-loop flag — and said to pick one openly instead of defaulting to whatever was easiest. Our answer is deterministic content-word overlap.

// Recall of the claim's content words in the cited evidence, in [0,1].
export function supportScore(claim: string, evidenceText: string): number {
  const want = contentTokens(claim);          // stopwords removed, lightly stemmed
  if (want.size === 0) return 1;
  const have = contentTokens(evidenceText);
  let hit = 0;
  for (const t of want) if (have.has(t)) hit++;
  return hit / want.size;
}

Default threshold 0.18, configurable in one place (REGISTRY_CONFIG.supportThreshold).

WHY RECALL
Not F1, not Jaccard

Evidence is allowed to say much more than the claim — a segment is usually longer than the sentence summarising it. But a claim should not assert content that appears nowhere in what it cites. That asymmetry is exactly recall.

WHY NOT AN LLM JUDGE
It has to be showable

An LLM judge would be more semantically accurate, and is the obvious upgrade. It also adds a model call to every extraction and cannot be demonstrated as deterministic on stage. Overlap is free, instant, reproducible, and explainable: here is the score, here is the threshold.

The category error the tests caught

Tier 2 originally ran on every field. The first test run failed, and the failure was more interesting than a bug.

The intent label price-sensitive scored 0.00 against its own evidence — "the pricing is the real problem though one four oh oh a seat is hard to justify" — and got flagged as unsupported. The classification was correct. The scoring was measuring the wrong thing.

An intent label is a classification, not a restatement of what was said. It will essentially never lexically overlap its own evidence. Applying claim-support scoring to it is a category error.

So the line was drawn where it belongs: tier 2 gates assertions about what was said; tier 1 gates everything.

The support score is still computed and stored for the exempt fields, so the choice stays auditable rather than invisible.

Drop vs flag — an asymmetry, stated openly

LIST CLAIMS
Dropped

objections, next_steps, key_moments with unresolvable citations are removed. There is always a coherent output without them — an empty objections list is a correct answer.

SINGLETON DELIVERABLES
Flagged, never silently dropped

intent and follow_up_email are single objects. Deleting them leaves a hole a reader misreads as "no objections found". They ship marked unverified, with unresolvable ids stripped, and force run_status to partial.

Either way, nothing ships as though it were grounded when it is not, and every decision is logged.

How run_status is decided

StatusCondition
shippedNo rejections at all. Everything passed clean.
partialSomething was dropped or flagged, but at least one claim survived verified.
failedClaims were attempted and nothing held up. Not a cheerful partial — a failed extraction.
deadlineThe budget governor stopped the run before it could finish. Set by the loop, not the gate.

Worked examples

These are real cases from scripts/test-gate.ts, run against a real transcript.

i

Four cases, and what the gate does

·
A well-cited claim → verified, shipped

Claim: "Pricing is hard to justify at that per-seat cost", citing seg_003.

Segment seg_003: "the pricing is the real problem though one four oh oh a seat is hard to justify"

Tier 1 resolves. Tier 2 scores 0.67 — content words pricing, seat, hard, justify all present. Verdict verified, run_status: shipped, evidence attached with the segment's real timestamp of 15,280 ms.

A fabricated segment id → dropped and logged

Claim: "The prospect said their legal team blocked the deal", citing seg_999 on a ten-segment call.

Tier 1 fails. The claim is removed from the output. A rejection row is written:

field:   objections[1]
reason:  unresolvable_citation
detail:  Cited seg_999; no such segment in this call. Claim dropped.
dropped: true

The legitimate claim alongside it survives untouched, and run_status drops to partial.

A real segment that does not support the claim → flagged, not dropped

Claim: "The prospect confirmed budget approval and a signed purchase order", citing seg_000 — which is the rep's opening pleasantry.

Tier 1 resolves, so the claim is not deleted. Tier 2 scores 0.00. The claim ships marked unverified with an amber badge reading "support 0.00", and a rejection is logged with dropped: false.

This is the case that would be invisible in any other tool: a citation that looks fine and points somewhere real, but does not say what the claim says.

A partly-bad citation list → keeps the good ids, drops the bad

Claim citing ["seg_003", "seg_777"]. The gate keeps seg_003, discards seg_777, logs the partial failure with dropped: false, and the claim ships with one accurate receipt instead of two — one of which was fiction.

The proof

23 checks in npm run test:gate, all passing. They assert behaviour by forcing the failure, not by reading the code:

clean draft → shipped, 0 rejections fabricated id → dropped + logged legit claim survives alongside it unsupported → flagged, not dropped no citation at all → dropped nothing holds up → failed, not partial partial list → good ids kept evidence text comes from the segment evidence carries the segment's real timestamp

There is also a live demonstration wired into the app. POST /api/demo/gate-check feeds hand-written claims — three that resolve, two that cite non-existent segments — through the real gate and returns what happened. It is reachable from any call page via Test the gate.

It is labelled honestly in both the API response and the UI: no model is called, and it is not pretending a model hallucinated. Waiting for a real hallucination on stage would be a bad bet; inventing one and implying the model produced it would be dishonest. So it says plainly that the claims are injected, and lets you watch the gate work on them.

What the gate cannot do

The gate verifies that a quoted claim matches the transcript. It has no way to know whether the transcript itself is faithful to the audio.

That is not hypothetical. PyAI Hear has been observed fabricating fluent, confident sentences from room ambience on the streaming path — text nobody said, at 0.99+ confidence. If a transcript segment contains invented speech, a claim citing it passes the gate cleanly, because from the gate's point of view the quote is right there in the transcript.

Our ingest uses the batch path, which has not been measured for this behaviour. It is the single most consequential open question about the product's core guarantee — see §10.
